# Changelog

The release notes of every version, newest first: the same text as the [releases page](https://github.com/zenetys/hyoai/releases), without its screenshots.

This file is generated by `node scripts/changelog.mjs`: edit the release notes, not this file.

## [1.4.3](https://github.com/zenetys/hyoai/releases/tag/v1.4.3) - 2026-11-12

This release adds a Changelog page to the Settings window, with the release notes of every version, and a changelog file to the repository.

### The Changelog page

The navigation of the Settings window ends with a Changelog entry, pinned at the foot of the list whatever the height of the window, with the version of the build, such as 1.4.3, at the end of its row. The page lists the release notes of every version, newest first, each with its date. The installed version is marked and open. For the older ones the page shows the text that introduces the release, and a button opens its titled sections. A button at the top opens the releases page on GitHub.

The notes are the ones published on GitHub, without their screenshots, and they are written in English whatever the language of the interface. The page is loaded when it is opened, so it adds nothing to the start of the application, and the address `?settings=changelog` opens it. The embedded widget does not offer it. The version is the one in `package.json`, read when the application is built, so it is the same in every deployment of a build.

### A changelog file

`CHANGELOG.md` at the root of the repository gathers the same release notes, newest first, with a link and a date for each. It is for the readers who do not have the GitHub releases at hand, such as a clone, a fork or the internal Git server of a company.

The file is written by `scripts/changelog.mjs` from the published releases, so it is the same text as the releases page and is never edited by hand. The script needs the GitHub CLI signed in to the repository. Before a release is published it takes the notes of the version to come from a file, so that the changelog that ships with a release already lists it. The page reads the file through `data/changelog.json`, which the same script writes from `CHANGELOG.md` before `npm run dev`, `npm run build` and `npm run check`, with no network, and which Git does not keep.

Nothing has to change when upgrading from 1.4.2: `config.json`, local overrides and stored settings are read as before.

### Documentation

The features guide describes the Changelog page and the address that opens it. The README lists the changelog among the guides and the script in the structure of the repository.

## [1.4.2](https://github.com/zenetys/hyoai/releases/tag/v1.4.2) - 2026-11-12

This release replaces the Modalities JSON field of the model form with two selects, and makes the `?settings` link work on its own and follow the dialog.

### Image and audio attachments without JSON

In the detail of a model, under Advanced settings, the Modalities (JSON) field is gone. Two selects take its place, Image attachments and Audio attachments, each set to Auto, Yes or No, like Supports thinking and the other capability selects around them. Auto leaves the key out of `config.json`: the attachment is then on only when the server reports the modality, which a llama.cpp endpoint does through `/props`, and off otherwise. Yes or No forces it, whatever the server says. A short line under the first select says so.

The selects read and write the same `modalities` key as before, so `config.json`, local overrides and the Generated JSON are unchanged: `{ "image": true }` shows as Image attachments set to Yes and Audio attachments on Auto. Only the `image` and `audio` keys are read, so any other key written inside `modalities` is dropped when the form builds the configuration.

### The settings link

A bare `?settings` now opens the Settings window, on its first screen: Appearance on a wide screen and the list of pages on a phone. Until now only a link that named one of the nine pages did.

The address bar also follows the window from the start. Opening Settings from the header or from the command palette on a wide screen gives `?settings=appearance`, the page on screen, where it used to stay without a parameter until a page was picked. On a phone, where the first screen is the list of pages, the address carries a bare `?settings` until a page is picked. In an embedded widget, a page the view hides is replaced by the first page it shows, and the address names that one. Closing the window removes the parameter, as before, and a value that is not one of the nine pages is still ignored.

Nothing has to change when upgrading from 1.4.1: `config.json`, local overrides and stored settings are read as before.

### Documentation

The models guide lists the two attachment selects in place of the Modalities (JSON) row, and the features guide describes the parameter written when the window opens and the bare `?settings`.

## [1.4.1](https://github.com/zenetys/hyoai/releases/tag/v1.4.1) - 2026-11-12

This release makes the generated JSON of the Configuration page safe to paste over `config.json`, adds a `thinking.disabled` option for models that do not reason, and fixes a few details of the sidebar and of the switches.

### A generated JSON that loses nothing

The Generated JSON preview of the Configuration page, and its Copy button, now include the root keys that no page edits: `notice`, `placeholders`, `embedOrigins` and any key the application does not know. They come after the keys of the form and are written as they are in the file. The copied JSON can therefore replace `config.json` as it is, where it used to leave these keys out and the guides told you to put `embedOrigins` back by hand. That advice is gone from the documentation.

### Models that do not reason

A model entry can now set `"thinking": { "disabled": true }`. The model then has no Thinking switch and neither fragment is sent, not even the global one. Until now an entry whose switch was hidden with `supportsThinking: false` still received the `on` fragment of the global `thinking` while the state was on, which is what this option stops.

`disabled` wins over `supportsThinking` and over any `on` or `off` written next to it. It only applies to the entry that carries it, and the effort levels are not affected. In the application it is typed in the Thinking (JSON) field of the model, under Advanced settings, and it goes through the form unchanged.

### Sidebar and switches

When the window is narrower than 768 px and the sidebar is a sheet, the card shown while hovering a conversation opened to the right of the sheet and ran off the window. It now opens under the row and stays inside the window.

The sidebar rows, the content matches, the conversation title in the header and the rows of the Export and Reset dialogs now fade in and out on hover instead of switching at once. The shortcut hints on the New conversation button and the search field, Ctrl/Cmd+Shift+O and Ctrl/Cmd+K, are no longer shown on touch devices or in the sidebar of an embedded widget, where those shortcuts do not exist.

The thumb of a switch could sit one pixel off the vertical centre of its track at some positions on the page, including at 100 % and 125 % zoom. The track is now a whole number of pixels high and the thumb is centred at 100 %, 110 %, 125 % and 150 %. At zoom levels below 100 %, such as 90 % and 80 %, it can still be one pixel off, because the track is not a whole number of device pixels there.

Nothing has to change when upgrading from 1.4.0: `config.json`, local overrides and stored settings are read as before.

### Documentation

The models guide describes `thinking.disabled` and the root keys kept by the generated JSON. The embed and features guides say that the sidebar shortcut hints are hidden on touch devices and in the widget.

## [1.4.0](https://github.com/zenetys/hyoai/releases/tag/v1.4.0) - 2026-11-10

This release rebuilds the Settings window as a navigation list with one page per topic, a search box and a `?settings=` link that opens a given page. It also adds a notice strip and rotating placeholders that an administrator sets in `config.json`, and it opens the composer menus as bottom sheets on narrow or touch screens.

### A new Settings window

The Settings dialog is no longer a set of five tabs. It is one window with a navigation list on the left and one page at a time on the right, under a title bar that runs across the top. There are nine pages in four groups separated by a thin line, without group titles: Appearance and Behavior; Models, MCP servers and Tools; Data and Configuration; Sampling and Chunking. The generation settings come last because they are the most technical.

Each setting is a flat row. The label, and a short grey explanation when there is one, sit on the left and the control sits on the right, with thin lines between the rows and no box around them. Wide controls such as the system prompt sit under their label. The values and defaults are unchanged; only their place in the interface has moved. The model availability settings are at the top of Models, the chunking and compaction settings are on Chunking, the sampling and penalty settings are on Sampling, the MCP servers have their own page, and the editing of the models left Configuration for Models. Each of the other pages keeps what the matching tab had.

The skin selector is now called Style, both in the Settings row and in the header switcher. The skins and the default Soft are unchanged, and the word Appearance only names the Settings page.

In an embedded widget, Appearance, Behavior, Sampling and Chunking are shown, and Data only in the sidebar variant. Models, MCP servers, Tools and Configuration are never shown, so the widget no longer offers the model availability settings, which were on its General tab, and uses their defaults. The Appearance page of a widget leaves out Theme, Style and Interface language, which the host page owns, and the search skips them too. The title bar of an embedded Settings window has an "Open the full app" button. A link that names a page the widget hides opens the first page shown on a wide screen, and the list of pages on a phone.

Nothing has to change when upgrading from 1.3.2: `config.json`, local overrides and stored settings are read as before.

### Search and links

A search box at the top of the navigation, "Search settings", filters the settings as you type. It looks at the name of each setting and at its explanation, ignoring case and accents, and it also finds a page by its own name. The text you type is matched as one sequence of characters, so a two-word query has to appear exactly as written. Results are grouped by page. The individual models, MCP servers, tool providers and tools are not listed, although their three pages can be found by name.

Choosing a result opens its page, scrolls to the setting and puts the keyboard focus on its control, and choosing a page heading opens the page itself. A few rows have no control to focus, such as the four blocks of the Data page, so only their page opens. When nothing matches, the dialog says so. Escape clears the search first and a second Escape closes the dialog.

While a page is open, the address bar carries `?settings=` followed by the page: `appearance`, `behavior`, `models`, `servers`, `tools`, `data`, `config`, `sampling` or `chunking`. Closing the dialog removes the parameter, and loading a link that carries it opens Settings on that page, so you can send someone straight to the right place. A value that is not one of these nine is ignored and the dialog does not open. The parameter does not add entries to the browser history. Opening Settings from the header or from the command palette does not write it: a wide screen shows Appearance, a phone shows the list of pages, and the parameter appears once you pick a page.

### Models, MCP servers and Tools

The Models page opens with the Model availability group. It holds "Automatically disable unavailable models" and "Check a silent server after (seconds)", which used to be on the General tab.

Below it is one row per model, with its name, its server type and the host of its base URL. A Disabled badge appears on a disabled model, a switch enables or disables it in place, and a chevron opens its detail, with a breadcrumb back to the list. The detail holds Enable model, Identifier, Model id, Display name, Short name, Base URL, Server type, API key, Streaming and Send context, then a collapsed Advanced settings section where the scope of MCP servers for the model is. Move model up, Move model down and Remove model are at the bottom. Add a model puts a new entry at the top of the list and opens it.

Edits are applied live as a local override of `config.json`, as before, and an edit made just before you leave the page is now saved instead of being lost. If a JSON field of a model, such as Headers or Thinking, holds invalid JSON, the page names the field under the list and the edit is not applied until the JSON is valid. The Override active badge, which only existed on the old Config tab, now also shows on Models, and only while a local override exists. It reads Override inactive when the configuration is invalid. On Models, clicking the badge leads to the reset dialog, and Configuration keeps its Reset… button.

The MCP servers page replaces the cards that sat at the bottom of the Tools tab. Each server is a row with its name, its address, a state pill, a switch and a chevron. An enabled server is connected while the list is shown, so the pill tells you whether it works without opening it. In the dark theme the Off pill now has a visible background.

The detail of a server keeps the controls of the old card: its origin (`config.json`, Changed here or Added here), the form, Remove with its Undo toast, Back to config.json for a changed server of `config.json`, and Restore under Removed from config.json. For an enabled server it also has the Tools list, collapsed until opened, with a Refresh button. Cancel in the form now puts the fields back to the server as stored, and for a CORS blocked or Local network state the raw error text is no longer repeated under the explanation. Add a server opens a New server page with the same fields as before.

The tools of a server each have their own approval select and, when the server declares them, the Read-only, Destructive or Reaches outside badges followed by "declared by the server, not verified".

The Tools page keeps the settings of the tool loop and the providers, and it no longer lists MCP servers. It holds Enable tools in new conversations, Maximum steps per answer, Default approval and Result size limit, followed by the Tool providers with an approval select per tool and the Reset approvals button. The "Manage in settings" link at the end of the tools panel of the composer opens the MCP servers page when the panel lists at least one MCP server, and the Tools page otherwise. It always opened the Tools tab before.

### A notice and rotating placeholders

Two new optional root keys of `config.json` let an administrator shape the first minutes of use. Neither has a field in Settings: they are edited in the file only.

`notice` shows a thin strip across the top of the application. Its `text` maps a language code to the message, and an optional `short` gives a shorter message for narrow screens. The language used is the one of the interface, then `en`, then the first one written. `level` is `info`, a quiet strip and the default, or `warning`, an amber one with an icon.

`until` is the last day shown, as `YYYY-MM-DD` taken to the end of that day in the reader's time zone, or a full date-time. Add an explicit offset, such as `2026-12-01T18:00:00+01:00`, for a single cut-off moment. After that, the strip is no longer rendered, and a value that cannot be read is dropped, so the notice then has no end.

By default a reader can close the strip with a Close button, and it stays closed in that browser until the `text` or `short` words change. Changing `level`, `until` or `dismissible` does not bring it back, and with `dismissible` set to `false` there is no button.

A malformed notice is dropped without affecting the rest of the configuration: an empty text drops the whole notice, while a bad `short` is ignored on its own. The notice is never shown in an embedded widget.

`placeholders` maps a language code to a list of texts, with the same language fallback as `notice`. Empty and non-text entries are skipped. In the empty message box of a conversation that has no message yet, these texts replace "Send a message...". They change every five seconds, in order and then from the start again: the old text tips away and the next one comes up in a short rotation. The rotation waits while the browser tab is hidden, and a single text is shown without rotating. Compare panes, conversations that already have messages and answers being generated keep the usual placeholder. So does a reader whose system asks for reduced motion, and in that case no configured text is shown at all. Unlike `notice`, `placeholders` also apply in an embedded widget. `public/config.example.json` carries an example of `placeholders` in English and French.

### Touch and narrow screens

On a phone, below 768 px, the Settings dialog is two screens. The first one is the search box and the list of pages, with a chevron at the end of each row. Opening a page shows it with a back arrow in the title bar, where the page name replaces "Settings". The on-screen keyboard stays down when Settings opens and comes up only when you tap the search field. Fields, selects, buttons and switches have larger touch areas, and label and control stack in the text rows and on the Data page.

The tools panel of the composer and the attachment menu, the + button, open as a bottom sheet when the window is narrower than 768 px or the main pointer is a touch screen, and as a popover or a dropdown otherwise. The tools panel sheet can be dragged down to close, and its "Manage in settings" row is larger. The attachment menu lists Images, Audio files, Text files, PDF files and System message, and an entry that needs a vision or an audio model says so under its label. An open menu keeps its state when the window is resized across the limit.

The dot that shows a call waiting for your approval now sits inside the corner of the Tools button, and the button is named "Tools" followed by the waiting call sentence while it is shown. The chevron of a submenu turns around when the submenu opens on the left because there is no room on the right. In Settings, the hint row under Send on Enter can no longer be reached with the keyboard while it is collapsed.

### Documentation

The guides describe the new window: the navigation, the search, the `?settings=` link, the phone screens and where each setting moved. They document `notice` and `placeholders` among the root keys of `config.json` and name the Style row. The README and the guides on models, MCP, tools, compare and the embed use the new page names. The screenshots of the guides are recaptured in the light and dark folders. The French interface also gets a few wording fixes.

**Full changelog**: [v1.3.2...v1.4.0](https://github.com/zenetys/hyoai/compare/v1.3.2...v1.4.0)

## [1.3.2](https://github.com/zenetys/hyoai/releases/tag/v1.3.2) - 2026-11-06

This release fixes the status of a tool call that showed up one step late, says plainly when a tool is hidden from the model, and makes the toasts follow the look of the rest of the interface.

### Tool calls

The status of a tool call could lag by one step: a call you had just approved still showed its pending circle, and the next call showed its check mark before it had answered. The cause was in the hook that reads a slice of a store. It did not read again when the selector it was given changed, so a component whose selector depended on its props kept the previous value until something else updated the store. The hook now reads again as soon as its selector changes, and the status follows the call.

### Hidden tools

The policy that kept a tool away from the model was labelled "Disabled", which read as if the tool itself were broken. It is now "Hidden from the model", in the settings and in the guides: the tool is not offered, so the model cannot ask for it, while the provider and its other tools stay available. A line under the Providers heading of the Tools tab explains it, and the policy selects are wide enough for the new label.

The count in the tools panel of the composer now shows it as well. A provider with one tool that is hidden from the model reads "1 tool · 1 hidden" instead of just "1 tool". The tool is still counted, and the suffix tells you why a model does not see a tool you left switched on.

### Toasts and settings

The buttons of a toast, such as Undo after removing an MCP server, now have the size, radius, colours and hover transition of the other buttons of the site, in the light and dark themes and in every skin. Clicking one while the Settings dialog is open used to close the dialog first and never reach the button, because the dialog treats the toast as an outside click and sets the page under it to ignore the pointer. The toast now takes the click and the dialog stays open. Undoing the removal of a server also shows a second toast, "{name} restored.", so you know it worked.

The description of the model availability setting is shorter: a model that stops answering is greyed out and left out of shared sends until its server answers again, and with the setting off it stays selectable and the error shows when you send.

### Documentation

The README and the tools and MCP guides use the new label, and the guides describe the hidden count in the tools panel. The screenshots of the tool settings, of an MCP server with its tools and of the model availability setting are recaptured with the new texts, in the light and dark folders.

## [1.3.1](https://github.com/zenetys/hyoai/releases/tag/v1.3.1) - 2026-11-06

This release fixes how the reasoning of a model is handled during tool calls, and a button that was cut off in the settings. A conversation that uses no tools, or a model that does not reason, behaves as before.

### Reasoning during tool calls

The `chat_template_kwargs.preserve_thinking` opt-in sends the saved reasoning of earlier steps back to a model whose chat template supports it. The opt-in was ignored for a model entry with Send context switched off, although such an entry still sends the current turn, tool steps included. The reasoning of the steps of the current flow now goes along with them.

When the calls are shown to the model as text, which happens when tools are switched off or the model cannot take them, a step that reasoned but wrote no text used to disappear from the history even with the `preserve_thinking` opt-in on. With the opt-in on, it is now sent as an assistant message with its reasoning and no text, as a plain reasoning-only message already was. Without the opt-in nothing changes: no reasoning is sent, and a step with neither text nor reasoning is still left out.

A step that follows tool results and ends with reasoning but no answer text and no call now gets its own error: "After the tool results the model only reasoned and wrote no answer. Regenerate the answer, or raise the maximum number of tokens if the reasoning uses them all." Such a step used to get the message for an empty answer. The new message is available in English and French.

### Settings

The last control of a settings tab, such as the Reset approvals button of the Tools tab, was cut off at the bottom of the scrolled area. The area now keeps a margin below it.

### Documentation

The screenshots in `docs/images` are now split into `light` and `dark` folders, with the same file names and without the `-light` or `-dark` suffix: `docs/images/light/tool-flow.png` replaces `docs/images/tool-flow-light.png`. The README and the guides use the new paths. Links pinned to a tag, such as the images of the 1.3.0 release, keep working. The tools guide has a new section, Reasoning during a flow, its table of errors lists the new message, and the models guide says that the opt-in applies with Send context off.

## [1.3.0](https://github.com/zenetys/hyoai/releases/tag/v1.3.0) - 2026-11-05

This release lets the application use the tools of MCP servers. A server declared in the configuration provides tools that appear next to the Clock provider and go through the same approval as the tool calling of 1.2.0. It also adds an opt-in recovery for tool calls that a model writes as plain text, reports answers that end without saying why, and extends the rule that keeps remote images out of replies that follow a tool result.

### MCP servers

An MCP server is declared in the new `mcp.servers` list of `config.json`, or added from the Tools tab of Settings. Each entry has an `id` (1 to 30 letters, digits, `-` or `_`), a `url`, and optionally a `label`, a `transport`, `headers` and `enabled`. The address is an http(s) URL or a path resolved against the page, which suits a reverse proxy on the same origin. Two transports are supported, Streamable HTTP and the older SSE. With the default `auto` the application tries Streamable HTTP first and falls back to SSE when the server does not know it. `http` and `sse` force one of them. An entry with an invalid or duplicate id, an unusable address (one that holds spaces or credentials) or an invalid header is dropped with a warning in the browser console, and the other servers and the models still load.

The application only lists and calls a server's tools. It does not use its resources or prompts, and OAuth is not supported: authentication uses static headers, typically `Authorization: Bearer <token>`. Because HYOAI runs in the browser, these headers are sent from the browser, and the ones written in `config.json` can be fetched by anyone who can load the page. `public/config.example.json` carries a disabled example server, and its vLLM entry shows `mcpServers` and `recoverToolCalls`.

In Settings, the Tools tab has an MCP servers section. Each server is a card with a status pill, a switch that offers or withdraws its tools, a pencil to edit it and a remove button, which shows a toast with an Undo button. The pill reads Off, Not connected, Connecting, Connected, or the kind of failure: Authentication (HTTP 401 or 403), Not found (404 or 410), No answer (timeout), Unreachable, Protocol error, and, for a server on another origin where the browser hides why the request failed, CORS blocked, or Local network when the server is on a local address and the page is not. A plain http server on a non-loopback address (not localhost, 127.x.x.x or ::1) behind an https page shows Unreachable instead. A loopback http server is treated as secure by the browser, so it shows CORS blocked like any other server on another origin. Under its address, a server that is not connected shows an explanation box: what the state means and, for a failure, the reason. For a CORS blocked or Local network failure, the box lists the response headers the server has to send for the page's origin.

The form behind Add a server asks for a name, an identifier (set once, for a new server), an address, a transport, a bearer token and other headers as JSON. The token field is masked until you reveal it and has a copy button, whereas the other headers are displayed in clear. Save stays disabled until the identifier, the address and the headers are valid. The token is stored as the entry's `Authorization: Bearer` header.

Servers added or changed here are kept in this browser as a difference on top of `config.json`, and each card says whether it comes from `config.json`, was changed here or was added here. A server of `config.json` that you removed is listed so that you can restore it, and the reset dialog of the Config tab lists these changes under MCP servers. Exports of your data contain no MCP server and no header, so importing a file does not bring them back. In the Generated JSON preview of the Config tab, the values of MCP headers are replaced by `********`, while the Copy button still copies the real values.

Nothing connects when the application starts. An enabled server connects the first time its tools are needed: when Settings shows its card, when you open the tools panel, or when an answer starts with tools on and a model that can take them. A tool list is reused for 30 seconds, and a failure is remembered for the same time, so for those 30 seconds a server that does not answer is not asked again before each message and its error is not repeated. If a server forgets its session, the application reconnects and repeats the request once, provided the request was refused before it ran. In Settings, the Refresh button next to Tools lists the tools again, or reconnects from scratch when the server is in error. In the tools panel, a failed server row has a Retry button that connects again. A server switched off is not contacted, and an embed registers no MCP server.

The tool list of a server is bounded to protect the model's context: at most 200 tools per server, and a tool with a missing, duplicate or over-long name, with an oversized schema, or that would take the server's tool list over a total size budget, is dropped. Longer descriptions and titles are cut, not dropped. The result of a call goes to the model as text. Images and audio returned by a server are replaced by a short note and are not passed to the model. A result flagged as an error by the server is shown as a failed call. A call is cut after 60 seconds like any other tool, and the result is limited by the size setting of the Tools tab.

An expanded server card lists its tools, each with its own approval select. The hints a server declares are shown as badges (Read-only, Destructive, Reaches outside), followed by the note "declared by the server, not verified". They are for display only and do not change any approval.

In the Tools tab, the MCP servers section comes after the options and the providers of 1.2.0, and the Reset approvals button stays at the bottom. In this example, tools are switched on for new conversations and Current time is set to Always allow.

A provider that does not list its tools within 10 seconds is left out of that answer, and a notice names it by its label (the server's label, or its id, for an MCP server) instead of its internal id. The tools of the other providers are still offered. In 1.2.0 the listing had no time limit. Stop now takes effect while the tools are still being listed, without waiting for the listing to end, and if you were continuing an interrupted tool exchange, its open calls stay as they were so that Continue still finds them.

### Choosing which servers a model sees

By default a model can use every enabled server. A model entry can now carry an `mcpServers` list of server ids to restrict it to those servers, and an empty list gives it none. A value that is not a list of strings counts as an empty list. The scope applies when an answer collects its tools, so it matters when tools are on and the model can take them. In the Config tab, the Advanced settings of a model have an MCP servers block with an Every enabled server switch. Turning it off lets you tick the servers the model may use. The servers themselves are edited in the Tools tab.

### Approvals and the tools panel

A call to an MCP tool waits for your decision the same way as in 1.2.0: allow once, always allow, or deny. The card now adds a "Tool name: ..." line under the title when the tool's own name differs from its title, for any provider. The title, the name of the server that receives the arguments and the "Declared read-only by its provider" badge are as in 1.2.0, and the badge, shown when the server declares the tool read-only, does not skip the approval. "Always allow" applies to a single tool of a single server, identified by its id and its address. If you change the address of a server, its tools fall back to the default approval instead of inheriting the earlier decision, which stays in the settings until you use Reset approvals. Changing only the headers, the transport or the name keeps the decision.

The wrench panel of the composer lists the MCP servers after the other providers, each tagged MCP, including the ones that are switched off. The switch of a server row is the same setting as the switch of its card in Settings, not a per-conversation one. Each row shows a status line: the error of a failed server with a Retry button, Off, Not offered to this model when the model's scope leaves it out, Connecting, the number of tools, or a note that the tools could not be listed. The panel stays within the window and scrolls when the list is long, and its "Manage in settings" link now looks like a row of the model menu.

### Models that write their calls as text

Some servers let a tool call leak into the text of the answer, in the markup format used by Hermes-style templates (`tool_call` blocks with a `function` and its parameters). A model entry has a new `recoverToolCalls` option, off by default, also available as the Recover tool calls written as text switch in the Advanced settings of the Config tab. When it is on, a call written that way runs like a normal call, with the same approval rules.

Recovery applies only in limited conditions. It applies only to a step of a tool exchange that produced no structured call and ended normally. It does not apply to an "Answer without tools" step. The block has to end the text and be complete, and every function name has to be one of the tools offered for that answer. Otherwise the text is left as it is, even when only one of several calls is wrong. Argument values are converted to the types declared by the tool's schema when the text allows it, and a call without parameters is recovered only for a tool that requires none. A recovered block is removed from the displayed text.

During a tool exchange, an answer that ends without saying why is now reported as an error on the message instead of staying silent, with a message that says what happened: the stream closed early, a call was cut off, a call was announced but never arrived, or the model returned nothing after a tool result. Half-written calls are not run. Outside tool exchanges, a stream of an OpenAI-compatible server that ends without a finish reason is now reported as an error with a suggestion to regenerate the answer, so a server that never sends a finish reason will show this error. The same check applies to the embed's headless runs. The summary written by conversation compaction (automatic or the Compact conversation action) is no longer stored when its stream is cut, so a half summary cannot replace the history, and a "Conversation compaction failed." toast is shown instead.

### Safety and interface

In 1.2.0, remote images were blocked in the answer right after a tool result. They are now blocked in a reply that has a tool result anywhere above it on its branch, and in the conversation summary that Free storage leaves in place of the folded messages. Such an image shows as a link reading "Image not loaded: " followed by its address, which opens in a new tab only when you click it. A final answer with no tool result above it, for example in a conversation that never used tools, still loads its images.

The native browser tooltips were removed from the conversation title in the header, so a truncated title no longer shows its full text on hover, and from the awaiting-approval icon in the sidebar. The relevance score of a source has a styled tooltip reading "Relevance score". Plugin tool providers can set an optional `policyScope`; an Always allow only applies as long as that scope stays the same.

### Documentation

Five guides join the embed guide in `docs/`: models, tools, MCP servers, compare mode with model availability, and a tour of the features. The embed guide now says what the widget leaves out. The README links them in a Documentation table. The new screenshots are in `docs/images`. The six old screenshots that the README used to display are removed, so a site built from this version no longer serves them under `/images/`.

## [1.2.0](https://github.com/zenetys/hyoai/releases/tag/v1.2.0) - 2026-11-05

This release lets models call tools. A tool is a function the model can ask for while it answers: by default every call is shown to you with its arguments and waits for your approval before it runs. The application ships a Clock provider with one tool, Current time, that returns the current date and time, to try it with, and plugins can bring their own.

### Tool calling

Tools are off by default. A new wrench button in the composer opens a panel with a switch for the open conversation and the list of tool providers, each with the number of tools it provides and a switch that is a global setting, not a per-conversation one. The button is tinted while tools are on, shows a dot when a call is waiting for approval, and is greyed out, with the reason, when the model cannot take tools. Every compare pane has its own wrench button in its header. In a single chat, a conversation that used tools and has them switched off shows a notice above the composer, as long as the model can take tools, with a button to switch them back on.

Unless a tool is set to always allow, when the model asks for a call the application shows the tool and its full arguments and waits for your decision: allow once, always allow this tool, or deny, in which case the model is told that you refused and goes on without that call. The call then runs and its result goes back to the model, which answers or asks for another call. Each of these round trips is a step. Calls run one after the other, at most 16 per step (the others are not run and come back as a "Failed" call with a message saying the limit was reached), and an answer stops after 10 steps by default: you can then continue, or have the model answer without tools. An answer that you stopped, or that a reload interrupted, before all its calls ran (for instance while one waited for a decision) can be continued the same way. The calls appear as cards in a block above the answer, each with its status, its duration, its arguments and its result, and regenerating, switching branch or deleting a message acts on the whole exchange; the answer that closes a tool exchange cannot be edited. The block opens by itself while a call waits for your decision, and the display setting "Expand search" becomes "Expand search and tool activity". A conversation waiting for an approval is marked in the sidebar and in its compare pane. The statistics in the footer of the final answer have a "Steps (time per step)" view that lists the time of each step and each call, and the sources returned by tools are gathered under the answer.

The Tools tab of Settings sets whether tools are on by default, for every conversation that has not set its own switch, the number of steps (1 to 50), the default approval (ask each time, or always allow, which shows a warning) and the size limit of a result. It lists every provider with its tools, each with its own approval (ask each time, always allow, or disabled, in which case the tool is not offered to the model), and a button resets the decisions you made.

### Servers and models

The server has to support tools, and some need a flag. llama.cpp must be started with `--jinja`; its entries read the chat template from `/props` (the `runtimeProps` option, on by default for this type) and mark the model as able to take tools when the template reports support, unless the entry sets `tools` itself. vLLM needs `--enable-auto-tool-choice` and a `--tool-call-parser`, and its entry needs `"tools": true`. Ollama and other OpenAI-compatible servers use `"type": "openai"` with `"tools": true`.

Three options are new on a model entry, and can also be set in the Config tab of Settings: `tools`, `parallelToolCalls`, which is sent to the server as `parallel_tool_calls` (true lets the model ask for several calls in one step, false forbids it, and when it is unset the server decides; the calls still run one after the other), and `supportsToolChoice`, which says whether the server accepts the `tool_choice` field and is off for `"type": "openai"`, which covers Ollama. `config.example.json` shows `tools` and `parallelToolCalls` on its vLLM entry. When a server rejects the tools, the error says how to fix it (the flag to add, or setting `tools` to false), and the model information dialog has a "Tool calling" row that says whether the model can take tools and whether that was detected from the chat template.

When a request carries no tools, because they are switched off for the conversation or the model cannot take them, the results of earlier calls stay in the context as text and the calls themselves are left out, so that the model does not imitate them. Compaction never separates a call from its result and leaves alone the turn that is still in progress.

### Safety

By default every tool asks before it runs. "Always allow" applies to one tool, never to a whole provider, and importing a file never brings back the approvals or the Tools settings of the application (the tools switch of a conversation does travel with it). A result is capped at 20,000 characters by default and shown as plain text, never rendered as Markdown or HTML, and a call is cut after 60 seconds of running. In the answer that follows a tool result, images are not loaded and show as links, which limits what an injected instruction can send out through an image address. Tools are never offered in an embed.

### Plugins and exports

A plugin can now declare tool providers next to its server types, and the contract is documented in `plugins/README.md`. Tool calls and their results are kept in the HYOAI and llama.cpp web interface JSON exports and read back by the import. A llama.cpp file keeps the calls, their arguments and their results, but not their timings, status or approval. The Markdown export leaves out the calls and their results; the OpenAI (JSONL) export leaves out the calls and keeps each result as text appended to the user message it answers. Earlier versions of the application reject a HYOAI JSON file that contains tool results.

## [1.1.0](https://github.com/zenetys/hyoai/releases/tag/v1.1.0) - 2026-11-05

This release makes the compare mode reliable, tells you when a model cannot answer instead of failing silently, and introduces build-time plugins so that server types specific to one deployment no longer live in the core.

### Compare

Several ways of losing a conversation in the compare mode are fixed: starting a new conversation in a pane no longer overwrites the previous one with an empty tree, a conversation deleted while it was shown in a pane no longer comes back, and closing a pane no longer moves the focus to the first one (it goes to the neighbour). A pane also keeps the model it was given: it is never silently replaced by another one when that model disappears from the configuration, it keeps showing it and says it is unavailable.

Closing a pane no longer stops its generation. The conversation keeps running in the background, shows up in the sidebar while it works, and can be opened again at any time. When only one pane is left, the compare mode ends and the remaining conversation continues as a normal chat, with its model, its reasoning level and its effort, without being interrupted. Opening a conversation from the sidebar, from the search or from Ctrl+K now lands in the focused pane, a link to a single conversation opens it outside the compare, and the mobile menu has a "Single conversation" entry. The text and attachments typed in the composer follow you when you enter or leave the compare.

### Model availability

Models that cannot answer are now reported instead of failing at the end of a request. A model whose server is unreachable, whose entry is disabled, or that is no longer listed by its server is greyed out in the selectors with the reason and a Retry button. In a single chat the composer is blocked with the same reason, and in the compare mode the pane is greyed and left out of the sending ("Sending to 2 panes of 3"); Stop and the analysis only concern the panes that receive. Nothing is ever switched to another model behind your back.

A new setting in General, "Automatically disable unavailable models" (on by default), controls this. Switched off, an unreachable model stays selectable and the error is shown when you send. Model list and runtime property requests now time out after 10 seconds. During a response, a server that sends nothing for 20 seconds by default (adjustable in the same part of General, from 0 to 600, 0 turning the check off) is probed, and the request is given up only if that probe finds the server down. A slow but reachable server, such as a llama.cpp running on CPU only, is never cut.

### Plugins

A new `plugins/` folder, ignored by git, lets you add server types at build time: drop a folder in, restart `npm run dev` or run `npm run build`, and it is picked up. Without it the application builds and runs as before. A plugin can bring its own server type, its own translations, and report what it does through generic activity, citation and stage events, which are rendered the same way for every plugin. A model entry whose type no installed plugin handles is kept in the configuration and shown as unavailable, with an explanation. The README documents the contract.

The transport that was specific to one private backend now lives in a plugin instead of the core. Conversations stored by earlier versions are upgraded to the generic format when they are read or imported, and importing a file exported by HYOAI no longer drops the reasoning toggle, the effort, the chunk markers or the feedback of a message. The screenshots showing that backend were removed from the README.

### Other changes

- A model override stored in the browser is dropped as soon as an edited `config.json` says the same thing, so it no longer hides later changes to the file.
- The "finished" mark in the sidebar only plays on the row that has just finished.
- Opening a page other than the home page no longer starts the application setup (migrations, config loading, conversation loading) a second time.
- Next.js is updated to 16.4.4, zod 4.6.7 or later is required, shadcn moves to the dev dependencies, and `next dev` no longer writes agent rule files into the repository.

## [1.0.0](https://github.com/zenetys/hyoai/releases/tag/v1.0.0) - 2026-10-06

HYOAI (**Host Your Own AI**) is a chat interface for any OpenAI-compatible LLM that runs entirely in the browser. There is no backend to deploy or secure: the page talks directly to your inference server, and conversations never leave the browser. This first public release is the client we use at Zenetys to test, compare and benchmark models across backends.

### Highlights

#### Bring your own model

Point HYOAI at llama.cpp, vLLM, Ollama or any public OpenAI-compatible API, and switch between them from the model menu. Endpoints are declared in a single `config.json` that can be edited without rebuilding, and models are discovered from each server's `/v1/models` when none is pinned.

#### Compare models side by side

Compare mode sends one prompt to up to four panes at once. Each pane keeps its own model and reasoning settings, and the layout (panes, models and reasoning choices) lives in the URL, so a comparison can be bookmarked and reopened, or shared to reproduce the same setup on another browser.

#### Reasoning you can read

Thinking is shown in a collapsible block under each answer, next to per-message statistics (tokens, speed, duration). When a model declares them, a thinking toggle and an effort level are available from the composer.

#### Conversations that stay yours

Conversations are stored compressed in the browser, with a usage gauge and JSON export and import. Editing or regenerating a message creates branches you can switch between, and any message, or a selected passage of it, can be quoted to anchor the next question.

#### Built for daily use

Answers render Markdown, tables, highlighted code and source citations. Images, audio, text files and PDFs can be attached; images and audio are offered only for models that declare or advertise those modalities. On mobile, menus open as bottom drawers within thumb reach, and the whole interface is keyboard-accessible.

#### Embeddable

The same static build doubles as a compact widget: load it in an iframe with `?embed=1`, force a model, a theme and a locale from the URL, and drive it from the host page through `postMessage`, for the origins listed in `embedOrigins` in `config.json`. See [docs/embed.md](https://github.com/zenetys/hyoai/blob/master/docs/embed.md).

### Getting started

```bash
npm install
cp public/config.example.json public/config.json   # declare your endpoints
npm run dev                                         # http://127.0.0.1:4117
```

`npm run build` produces a fully static `out/` directory that can be served from any static host. HYOAI ships no model: the [README](https://github.com/zenetys/hyoai#bring-your-own-llm) gets a local one running in a couple of minutes.

Try it online: [tools.zenetys.com/hyoai](https://tools.zenetys.com/hyoai/)
